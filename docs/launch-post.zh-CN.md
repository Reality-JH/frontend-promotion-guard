# 后端构建是绿的，前端仍然可能是坏的

后端开发者通常会看几个信号：镜像构建成功，健康检查通过，接口返回 200。

这些信号有用，但对浏览器不够。

页面可以成功返回 HTML，同时 CSS 已经丢失、没有编译，或者静态资源路径指错。容器仍然健康，负载均衡仍然满意。用户打开页面，却看到布局已经悄悄坏掉。

当前端不是你的主战场时，这种问题尤其折磨人。你不需要再引入一套设计系统。你需要的是一个小而稳定的答案：

> 用户实际拿到的页面，是否还和我们批准的页面一致？

## Frontend Promotion Guard

[Frontend Promotion Guard](../README.zh-CN.md) 就是为这个问题做的发布门禁。

它先检查构建后的 CSS，再用真实 Chrome 或 Edge 打开运行中的页面并检查计算样式。它按配置访问多条路由和多个宽度，与受保护的视觉基线比较。使用 Docker 发布时，它会先在隔离端口启动候选容器，验收通过后才晋升；正式复验失败时，恢复之前保存的镜像。

顺序很重要。容器健康，不等于页面可以晋升。

## 它能拦截什么

示例项目包含两条路由和四档宽度，检查包括：

- 构建产物里残留 `@apply` 等源指令。
- 构建后消失的必需选择器。
- 关键元素的计算 `display` 发生变化。
- 目标宽度下的横向溢出。
- 浏览器控制台错误。
- 超过阈值的截图差异。
- 候选容器验收通过，但当前正式容器保持不变。
- 正式复验失败后自动恢复上一镜像。

它不能替代功能测试、安全测试、可访问性检查或人工验收。它只处理一个更窄的问题，并让这个问题更难被漏掉。

## 本地运行

```bash
npm install
npm run build
npm run example:build
npm run example:serve
```

另开一个终端：

```bash
node dist/cli.js baseline update --config fpg.example.yml
node dist/cli.js verify --config fpg.example.yml
```

第一条命令必须显式执行。测试失败不能覆盖基线。第二条命令会在 `release-evidence` 下生成静态报告，其中包含基线图、当前图、差异图、commit、检查结果和回退状态。

如果想看失败路径，可以启动示例里的破坏 CSS 服务，再使用 `fpg.broken-test.yml` 验收。页面仍会返回 HTTP，但计算样式检查会失败。

## 为什么后端主导的团队会需要它

发布契约可以贴近你已经拥有的工程流程：

1. 构建前端。
2. 启动候选服务。
3. 用 YAML 配置执行一条命令。
4. 失败时上传证据目录。

它不要求你引入云端 Dashboard，也不要求更换部署平台。它使用 Node、系统浏览器和可选 Docker。路由、选择器、视口、端口、镜像名、阈值和证据目录都在配置里。

这样，前端发布质量就能被 API、worker、队列和容器团队一起维护。

## GitHub Actions

仓库包含可运行的 Vite/React 工作流和跨平台矩阵。正式仓库与 `v0.1.0` tag 创建后，最小接入是：

```yaml
- uses: Reality_JH/frontend-promotion-guard@v0.1.0
  with:
    config: fpg.yml
    command: verify
```

失败时上传 `release-evidence`。报告是同事可以直接打开的文件，而不是一个没有解释的绿色勾。

## 一个边界清楚的小工具

Frontend Promotion Guard 不承诺页面一定正确。它拒绝只凭构建结果、HTTP 状态和容器健康就宣布发布安全。

如果你的团队曾经因为“技术上健康、视觉上损坏”的发布被叫醒，这就是它要补上的缺口。
